# Verify the mission's outcome

Choose the relevant checks; do not force every mission through every profile.
For mixed work, verify each required deliverable. Record each criterion's method,
outcome, current target version, and concrete evidence; no fixed tool stack.

## Code

Record baseline behavior and existing edits. Reproduce the relevant defect or
measurement before changing it when needed. Run the project's applicable checks
and confirm the requested behavior improved. A green unrelated build is not
proof. For performance, compare under the same conditions. Keep changes within
the authorized targets. Commits/PRs are deliverables only if requested; tests
passing does not authorize merging, deployment, or publishing.

## Research

Record questions, source/date scope, and intended deliverable. Read the supporting
source, distinguish publication time from observation time, and connect factual
claims to evidence. Prefer primary sources for technical claims. Check freshness
when the claim can change. Compare conflicting evidence rather than choosing a
convenient snippet. State inferences and material unknowns beside the claim.

Use the user's requested evidence scope. If they explicitly provide an
unavailable source and ask for a comparison with unknowns, a checked report of
available findings and those gaps can satisfy the reporting criterion. Do not
invent full access as an extra requirement or ask them to accept a limitation
they already stated. Never mark the missing factual comparison as verified.
If access or a definite answer is itself required, keep that criterion unresolved
until an adequate permitted source resolves it or the user changes the scope.
A list of URLs, search count, or polished prose alone is not completion.
Resume from checked sources and remaining questions, not an assumed new scan.

## Documents

Identify reader, required content, source material, target file/document ID, and
allowed edit range. Check coverage, factual/numerical agreement, clarity, and
format as relevant. Inspect rendered output when layout is part of acceptance.
Record a revision or file hash; check for intervening edits before writing back.
A draft being complete does not authorize sharing, sending, or publishing it.

## Monitoring and recurring work

Track last successfully checked sources/versions and reported deltas. Distinguish
successful no-change from failed access and partial coverage. Avoid reporting the
same item repeatedly. Do not advance the successful cursor past failed required
reads. A no-change pass ends that pass, not the ongoing mission. Persist the
result for the next invocation; schedule only through confirmed host support.

## Learning

Record reproducible failures with their scope and cause. Separate environmental
outages, stale sources, pre-existing failures, and regressions. Keep lessons
specific enough to reconsider when conditions change. Do not grow universal
NOT-OK rules from one unverified failure.
